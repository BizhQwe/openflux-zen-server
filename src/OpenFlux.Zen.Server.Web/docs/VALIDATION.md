# Проверки, 14 октября 2026

Обновление ядра до официального OpenFlux v0.7.3: весь upstream-diff перенесён, прежние локальные изменения проверены по снимку файлов и сохранены. Версия ядра в API и интерфейсе — 0.7.3; версия Zen Server — 1.0.0 для первого релиза. Дополнительные регрессии проверяют передачу подсказки размера пакета через Session, переопределение OPENFLUX_BATCH_BYTES и целость/порядок 128 KB данных в одном совместимом v2 сообщении.

Собраны ядро, панель, CLI и цельный установщик для Windows amd64/arm64/386 и Linux amd64/arm64/386/armv7. Windows amd64 и 386 проверены исполнением; Linux amd64 — в отдельной QEMU VM с Alpine Linux. Остальные цели проверены кросс-сборкой. Пользовательская VMware VM не изменялась. Предоставленная VPS проверена отдельно с резервной копией установки.

## Панель и совместимость

- Добавлена политика доступа: HTTP только для реального loopback и включённых частных CIDR; внешний HTTPS только с настроенными Host/SNI. Проверены подмена Forwarded/X-Forwarded-For/X-Real-IP/X-Forwarded-Proto, публичный IP/localhost Host, неверный/пустой SNI, отключение LAN/домена, IPv4-mapped IPv6 и обход с существующей сессией. Публичные и слишком широкие CIDR не принимаются. Публичные интерфейсы не используются для LAN-ссылок; сохраняется доверенный контекст встроенного HTTPS Localtunnel.

- HTTP localhost/LAN/IP и HTTPS домена работают на одном порту, с корректным Request.TLS. Проверены доменное перенаправление с сохранением пути/query, отсутствие перенаправления для IP/localhost и proxy backend, HTTP-ссылки localhost/LAN при настроенном TLS, готовность установщика по HTTP. Клиент без первого байта не блокирует другие соединения; остановка listener закрывает ожидающие соединения.

- Трафик: 25 MiB сжимаемых IPv4-пакетов через реальные batched/legacy кодеки учтены целиком, сжатый carrier меньше в десять и более раз. Контрольные пакеты исключены; неудачная Send не учитывается.
- TCP echo 25 MiB: на Windows учтены 27 475 096 / 27 348 684 байт IP-трафика с заголовками/повторными передачами; в изолированной Linux VM с прежним оригинальным клиентом — 27 362 252 / 27 245 776 байт. L3 interop и scoped nftables lifecycle проходят.
- Проверены время ядра вместо джиттера IPC, нулевые IP-счётчики, устаревший статус, сброс, простой, финальный снимок по IPC и завершение reporter при закрытии сервера.
- System: запуск/API-операции, уровни/время, восстановление истории и очистка; проверено отсутствие пароля, cookies, ключа и секретного маршрута. В браузере журнал заполнен, скачивание работает.
- Домен: HTTP/HTTPS на реальном порту, полный URL proxy, смена listen через API, HTTP→TLS на том же порту с сохранением текущего ответа, отказ занятого порта с сохранением чужого listener и прежних настроек.
- Плашка доступа удалена; обновление ссылки находится в нижнем блоке переключателей. В браузере проверены direct/proxy предпросмотры URL и отсутствие ошибок консоли.
- На предоставленной Ubuntu VPS успешно выпущен настоящий Let's Encrypt сертификат встроенным Go-клиентом; внешний HTTPS-запрос к порту 5000 проходит с проверкой сертификата. Вне выпуска сертификата 80/443 свободны.

- Тесты новых Go-модулей и `go vet` проходят на Windows amd64; тесты также проходят с GOARCH=386.
- Проверены HTTP-вход/выход, Origin, секретный маршрут, PBKDF2, локальные сессии, атомарный импорт старого JSON, ограничения серверной роли, cookies, IPC, встроенные ресурсы и отсутствие заглушек.
- Настоящее TCP echo через Direct и SOCKS5 проходит на Windows amd64/386 и Linux amd64. На Linux клиент отдельно собран из сохранённой старой копии исходного ядра; проверены L4 и L3 серверы, согласование ключа, исходная ссылка share, PNG QR и IPC-счётчики.
- На Linux выполнен полный набор тестов панели, configuration, CLI и его платформенного слоя, установщика и пакета L3 ядра. Два opt-in теста исходного L3, которым нужны отдельный namespace и изменённый MTU, пропущены с исходными условиями.
- Изменение пароля через HTTP-профиль обновляет защищённый локальный файл показа. API настроек/экспорта не отдаёт пароль; запрос файла .credentials через HTTP получает 404. Чтение credentials не меняет settings.json.
- Основной прежний интерфейс сохранён. PNG Avito не перерисован; скругление задано CSS. Предупреждение L3 удалено, добавлены запрошенные изменения Multi, статистики и QR.

## Статус, Multi, QR и секретный путь

- Cookies сохранены через авторизованный HTTP API без процесса ядра. Проверены состояние Stopped, выключенный автозапуск туннеля, сохранение прежнего account jar и чужих записей, раздельные jar Avito/Cups.online с пустыми URL, права 0600 на Linux и отсутствие доступа к файлу по HTTP. Повреждённый файл остаётся неизменным при отказе записи.
- Реальный процесс ядра запускает подписанный тестовый скрипт, который проверяет cookies в самом первом open(), до живых IPC-команд. Одиночный профиль и Multi проходят первый запуск и повторный запуск с теми же сохранёнными cookies. Окно cookies для остановленного туннеля предлагает «Сохранить куки».

- Регрессия имитирует комнату Avito, которая остаётся открытой после остановки клиента: peer_status становится disconnected. Клиент без трафика, продолжающий отвечать на heartbeat, остаётся connected. Classic показывает недавнюю активность вместо постоянного подключения к комнате.
- Реальный тест Direct/SOCKS5 останавливает клиентский процесс, затем проверяет, что сервер продолжает работать, а присутствие клиента и обе скорости обнулились.
- Потеря и восстановление Unix IPC проверены настоящим локальным сокетом: живые показатели сбрасываются и восстанавливаются без потери накопленных счётчиков. Зависший поток статуса ограничен 4 секундами.
- Авторизованный HTTP/IPC тест Multi отдельно отправляет cookies Yandex и Avito, проверяет Transport, изоляцию jar и сохранение запроса другого транспорта. Неизвестные и неподдерживаемые транспорты отклоняются. URL Телемоста проходит в собственный CLI-флаг.
- В браузере проверены Телемост в редакторе Multi, переключение отдельных черновиков cookies, отсутствие предупреждения L3 и скорость 0 B/s при сохранённом общем трафике. Ошибок JavaScript не обнаружено.
- QR длинной ссылки из семи транспортов (1936 символов) прочитан независимым ZXing как из исходного PNG, так и из снимка окна браузера; данные совпали полностью. Тест PNG проверяет целые пиксели на модуль, чёрный/белый цвет и поле в четыре модуля. Изображение загружается при прежней Content-Security-Policy.
- В браузере высота «Скачать PNG» и «Закрыть» равна 40 px; верхние и нижние края совпадают.
- Проверены генератор пути и первая установка: ровно 18 букв a-z/A-Z и цифр. Регрессия HTTP проверяет новый маршрут, закрытие прежнего маршрута и старой сессии. Обновление сохраняет старый zen-путь.

## L3 и TCP RST

- Защита реализована непосредственно на Go через [google/nftables](https://github.com/google/nftables), без запуска внешней команды nft/iptables. Проверка выполнялась также с PATH, в котором нет внешних инструментов.
- Реальный TCP-стек Linux создаёт RST в ответ на SYN-ACK для raw-соединения; тест подтверждает рост счётчика подавления этого RST.
- Клиентский RST, а также RST с другим исходным или целевым портом проходят; счётчик подавления не растёт. Обычный TCP к закрытому порту возвращает ECONNREFUSED.
- Проверены журнал восстановления после аварии, отказ изменять чужую таблицу, атомарный отказ создания и сохранение журнала при ошибке очистки.
- После остановки последнего L3-туннеля журнал и временная таблица удаляются. После всех проверок Linux nftables не содержит созданных проектом таблиц.
- Необязательная SO_MARK Linux raw-сокета относится к локальным метаданным и очищается перед выходом пакета; протокол, шифрование, кодеки и форматы ссылок не изменены. Самостоятельный запуск без переменной окружения сохраняет прежнюю обработку RST.

## CLI и установщики

- Первая установка генерирует независимые логин и пароль по 12 символов из a-z/A-Z/0-9. Проверены разные значения на новых установках, загрузка прежнего `admin` и пользовательского логина без перезаписи настроек. Реальные Windows x64/x86 установщики проходят HTTP-вход со случайным логином, вывод этих же данных через CLI и сохранение логина при повторной установке.
- Эти же изменения проверены исполнением нового Linux x64 установщика в отдельной Alpine VM: HTTP-вход со случайным логином, прежние логин/пароль после обновления, отмена удаления, отказ JSON-удаления без подтверждения, окончательное удаление каталога и обеих собственных ссылок команды openflux. Новые configuration/CLI регрессии проходят также на Linux.
- Удаление возвращено к оформлению прежнего CLI на RU/EN: рамка, `[INFO]`, подтверждение с отменой по Enter, `[WARN]` и `[OK]`. Регрессии проверяют отсутствие удаления после отмены, остановку службы перед удалением, отсутствие успешного итога при ошибке остановки, права и принадлежность службы до изменений, чистый JSON только с явным `--yes`. Реальные Windows x64/x86 установки удаляют также собственный работающий CLI и весь каталог; отмена оставляет settings.json неизменным.
- Help возвращён к прежнему оформлению и сокращён до start/stop/restart/status, autostart, credentials, uninstall и help. Команды network/reset/decoy больше не доступны.
- Подменённые контроллеры службы проверяют команды запуска/остановки/перезапуска, автозапуск и запрет изменений без административных прав.
- Реальные Windows x64/x86 установщики проверены в отдельных каталогах с пробелами: проверка встроенных хешей, извлечение трёх бинарников, openflux.cmd, вход по HTTP, смена пароля, показ через CLI, блокировка работающей панели, обновление старых имён файлов с сохранением settings/tunnels и пароля, полное удаление по умолчанию.
- Реальный Linux x64 установщик проверен установкой без службы в /opt/openflux-zen-server внутри тестовой VM. Регистрация __path создаёт оба symlink; пользователь nobody успешно запускает help/version/status через PATH=/usr/bin:/bin. Каталог установки доступен для выполнения CLI, data остаётся закрытым для других пользователей.
- Повторная Linux-установка показывает тот же пароль. Полное uninstall удаляет каталог и оба собственных symlink. Чужие файлы и alias не удаляются.
- Миграция старой hash-only установки проверена интерактивно: ввод скрыт, прежний пароль проверяется, settings.json сохраняется без изменений. Неверный и устаревший пароль не принимаются; при ошибке записи настроек кэш откатывается.
- Пункты размещения идут в порядке localhost, LAN/Wi-Fi, Localtunnel, домен. Дефолт нового мастера и уже выбранный режим сохраняют своё значение независимо от порядка пунктов. Строка «Автозапуск службы: true. CLI: openflux help» удалена.
- Проверены мастер RU/EN, три этапа, отчёт об ошибке, HTTP/HTTPS-готовность и итоговая карточка. --no-service сообщает об установке без запуска.
- Исправлена генерация systemd unit: WorkingDirectory не оборачивается shell-кавычками, literal-проценты экранируются, ExecStart отключает подстановку окружения. Регрессионные тесты проходят; основание — [парсер systemd](https://github.com/systemd/systemd/blob/main/src/core/load-fragment.c). На предоставленной Ubuntu VPS выполнены настоящий update установщиком, регистрация/запуск службы, HTTPS-вход и systemd-analyze verify unit. Windows-задача в разработке не регистрировалась.
- Загрузочные scripts/install.sh и install.ps1 ранее проверены с подменённой загрузкой, архитектурами и настоящим --verify установщика. Для настоящего скачивания нужно опубликовать Go-установщики и .sha256 в выбранном GitHub-репозитории.

## Воспроизведение

```powershell
go test ./src/OpenFlux.Zen.Server.Web/... ./src/OpenFlux.Zen.Server.Cli/... ./src/OpenFlux.Zen.Server.Installer/...
go vet ./src/OpenFlux.Zen.Server.Web/... ./src/OpenFlux.Zen.Server.Cli/... ./src/OpenFlux.Zen.Server.Installer/...
$env:OPENFLUX_TEST_CORE = (Resolve-Path .\dist\windows-amd64\openflux-zen-server-core.exe).Path
go test ./src/OpenFlux.Zen.Server.Web/internal/panel -run TestOriginalCoreInterop
```

В изолированной Linux VM/namespace:

```bash
sudo env OPENFLUX_TEST_NETFILTER=1 go test ./src/OpenFlux.Zen.Server.Web/l3guard
sudo env OPENFLUX_TEST_CORE="$PWD/dist/linux-amd64/openflux-zen-server-core" OPENFLUX_TEST_EXIT_MODE=l3 go test ./src/OpenFlux.Zen.Server.Web/internal/panel -run TestOriginalCoreInterop
```

Необходимы nftables в ядре Linux и сетевые права. Внешний TCP echo-сервер для интеграции можно задать через OPENFLUX_TEST_DESTINATION; отдельное исходное ядро клиента — через OPENFLUX_TEST_CLIENT_CORE.

## Существующие проблемы исходного ядра

Полный первоначальный прогон ядра на Windows имеет отдельные, воспроизведённые ранее проблемы:

1. provision.TestPinnedScriptHash: SHA-256 локального deploy/node-install.sh не совпадал с pin.go. После переноса обоих файлов из v0.7.3 тест проходит.
2. transport/yandex.TestDialIPv4FirstFallsBackToIPv6: IPv6 fallback не проходит на этом Windows-хосте.
3. tunnel.TestL4UDPDatagramRoundTrip/negotiated: непостоянный сбой проверки MTU при согласовании.

Первые два сбоя были воспроизведены в сохранённой старой копии. Это результаты прежнего полного прогона; обновление v0.7.3 устраняет первый из них.

Windows-процессы ядра находятся в Job Object с KILL_ON_JOB_CLOSE; Linux использует Pdeathsig. Основание Windows-механизма — [Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).
